# vov-365sd

Хобби-проект: анимация фронта 1941–42 под Ржевом с фокусом на боевой путь **365-й стрелковой дивизии** (место службы и гибели деда).

Идея и постановка: Obsidian → `Хобби/[идея] Анимация фронта 1941-42 под Ржевом (365сд).md`

## Разделение хранения

| Что | Где | Формат |
|---|---|---|
| Исходные материалы (сканы, PDF, фото, выгрузки) | Obsidian: `Хобби/365сд/Исходники/` | как получено, без изменений |
| Распознанный текст и переводы | **этот репозиторий**: `docs/sources/` | Markdown + YAML-заголовок со ссылкой на исходник |
| Геоданные (линии фронта, треки, точки) | `data/` | GeoJSON |
| Скрипты подготовки данных и сборки | `tools/` | Python / Node |

Правило: **исходник не копируется в проект**. В проекте лежит только md-производная, всегда с указанием, из какого файла в Obsidian она получена.

## Соглашения для md-производных

Файл: `docs/sources/<ГГГГ-ММ-ДД>_<КраткоеНазвание>.md` (дата = дата документа, не дата распознавания).
Один документ = один файл. Страницы разделяются маркером `<!-- page: N -->`.

Обязательный front-matter:

```yaml
---
источник: "Хобби/365сд/Исходники/имя_файла.pdf"   # путь внутри Obsidian vault
файл: "имя_файла.pdf"                              # имя исходника
страниц: 3
язык_оригинала: de        # de | ru
перевод: полный           # нет | полный | частичный
архив: "NARA T-315 R-…"   # если известно: архив, фонд, опись, дело
дата_документа: 1942-03-?
подразделение: "365 сд"   # о ком документ
статус: черновик          # черновик | выверено
---
```

Тело: сначала распознанный текст на языке оригинала (`## Оригинал`), затем перевод (`## Перевод`) — если перевод есть. Неясные места помечать `[?]`, не додумывать. Числа, фамилии, топонимы — как в документе, без «исправлений».

## Индекс

Реестр обработанных документов — `docs/sources/README.md`: одна строка на документ (файл-производная → исходник → краткое содержание → что даёт для проекта).

## Данные боевого пути (`data/`)

Машиночитаемый набор событий и формирований. Спецификация поведения — `openspec/specs/` (после архивации change) и `openspec/changes/add-combat-path-data-model/`.

Раскладка:

- `data/schemas/` — JSON-схемы (draft 2020-12): `fact`, `event`, `unit`, `source`, `registry`
- `data/registry.json` — перечень типов событий, уровней локализации, точностей даты, статусов
- `data/sources.json` — реестр исходников: `id`, путь в Obsidian, путь к производной, `sha256`
- `data/units.json` — формирования и периоды подчинения
- `data/events/<год>.json` — события; файл = год, `year` в файле обязан совпадать с именем файла

Правила, которые проверяются машиной:

1. **Каждый факт — объект** `{value, provenance, status}`; провенанс неотделим от значения. Конфликт: `{conflict: true, variants: [...]}` — минимум два варианта, статус выверки у конфликта не ставится.
2. **Провенанс** = `source_id` из `data/sources.json` + локатор (`page` / `slide` / `paragraph` / `quote`, минимум одно поле). Путь к производной и к исходнику в реестре обязан существовать, `sha256` исходника — совпадать.
3. **Статус `выверено`** допустим только при двух разных `source_id`; два локатора одного источника независимым подтверждением не считаются.
4. **Даты** — интервал `{from, to, precision}`; `precision: day` требует одинаковых границ, `month` — целый месяц, `range` — произвольный интервал, `null` — открытая граница. Неизвестная дата — обе границы `null`, а не выдуманные числа.
5. **Геометрия** — GeoJSON в WGS84 или `null`. Без геометрии уровень локализации обязан быть `approximate`.
6. **Провенанс блокирует сборку:** при любом нарушении `tools/build.py` не пишет артефакты.

Пополнение источников и фактов — **штатная операция, отдельный OpenSpec change не требуется**: меняется содержимое `data/`, а не поведение или контракт. Change нужен, когда меняется контракт (новый вид источника, новый тип локатора, схема) или поведение инструментов.

Как добавить событие:

1. Положить исходник в Obsidian `Хобби/365сд/Исходники/`, написать производную в `docs/sources/`, внести строку в индекс.
2. Зарегистрировать источник в `data/sources.json` (для замены скана — новый `id` с версией, старый не править).
3. Дописать событие в `data/events/<год>.json` с провенансом на конкретный локатор.
4. `python3 tools/validate.py` — должно быть 0 нарушений.
5. `python3 tools/build.py` — обновит хронологию и GeoJSON.

Команды:

```bash
python3 tools/validate.py                # проверки схемы и провенанса
python3 tools/build.py                   # хронология + data/dist/features.geojson
python3 tools/build.py --check           # только сравнить артефакты с данными
python3 -m unittest discover -s tests -v # тесты валидатора и сборки
```

Корень Obsidian берётся из переменной `VOV_VAULT` (по умолчанию `/home/anb/Documents/Obsidian Vault`), переопределяется флагом `--vault`.

Артефакты: `docs/research/Боевой путь — хронология (сгенерировано).md` (не редактировать вручную) и `data/dist/features.geojson` (в git не попадает). Ручной анализ — `docs/research/Бизяев ЕМ — сводка и расхождения.md`.

## Места и геоданные

`data/places.json` — реестр мест: `id`, названия, тип, `state` (`found` | `tract` | `unfound`), `accuracy` (`exact` | `settlement` | `district` | `approximate`), `region` для запросов, `coords` как факт (`{value: {lon, lat}, provenance, status}`) или `null`.

Правила:

1. Координата без провенанса не принимается; провенанс геоданных обязан вести на запись журнала `geo-<slug>` в `docs/sources/недат_Геокодирование Nominatim — журнал запросов.md` и на файл кэша `data/cache/geocode/<slug>.json`.
2. `found` и `tract` требуют координат, `unfound` — наоборот, их не имеет и не должен иметь. Событие может ссылаться на `unfound`-место: тогда оно остаётся в хронологии с пометкой «место не локализовано» и не попадает в GeoJSON.
3. Координаты — WGS84 в порядке «долгота, широта»; выход за `bbox` из `data/registry.json` (район проекта) считается ошибкой — так ловятся перепутанные широта и долгота и одноимённые селения в других регионах.
4. Кандидат геокодера принимается только при совпадении названия **и** района/области. «Малая Борщевка» — не «Борщёвка»; такие двойники попадают в реестр вручную через `names.alternate`, а не автоматически.
5. Событие, у которого есть и своя геометрия, и место, использует свою геометрию; иначе берётся точка места, а уровень локализации — из `accuracy` места.

Как добавить место:

1. Дописать запись в `data/places.json` (`state: unfound`, `coords: null`, `region` с районом и областью).
2. `python3 tools/geocode.py --all` — заполняет кэш из Nominatim (не чаще 1 запроса в секунду).
3. `python3 tools/geocode.py --all --apply` — переносит принятые кандидаты в реестр и перегенерирует журнал.
4. `python3 tools/validate.py` — проверить цепь провенанса.

Атрибуция и ограничения: координаты — OpenStreetMap / Nominatim, данные © OpenStreetMap contributors, ODbL 1.0. Запросы ограничены одним в секунду и имеют собственный User-Agent. Ответы кэшируются в `data/cache/geocode/` и коммитятся: проверки и сборка работают офлайн, `tools/validate.py` и `tools/build.py` в сеть не ходят вовсе.

```bash
python3 tools/geocode.py --all              # дозаполнить кэш (сеть)
python3 tools/geocode.py --all --offline    # только кэш
python3 tools/geocode.py --all --apply      # применить к data/places.json
python3 tools/geocode.py --journal-only     # перегенерировать журнал
```

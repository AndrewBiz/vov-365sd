# vov-365sd

Зеркала (обе публичные, содержимое одинаковое):
[github.com/AndrewBiz/vov-365sd](https://github.com/AndrewBiz/vov-365sd) · [gitverse.ru/kazimir_bizik/vov-365sd](https://gitverse.ru/kazimir_bizik/vov-365sd)

Пуш в оба: `git push github master && git push gitverse master` (remote'ы названы по хостам, `origin` нет).

Хобби-проект: анимация фронта 1941–42 под Ржевом с фокусом на боевой путь **365-й стрелковой дивизии** (место службы и гибели деда).

Идея и постановка: Obsidian → `Хобби/[идея] Анимация фронта 1941-42 под Ржевом (365сд).md`

## Разделение хранения

| Что | Где | Формат |
|---|---|---|
| Исходные материалы (сканы, PDF, фото, выгрузки) | Obsidian: `Хобби/365сд/Исходники/` | как получено, без изменений |
| Распознанный текст и переводы | **этот репозиторий**: `docs/sources/` | Markdown + YAML-заголовок со ссылкой на исходник |
| Геоданные (линии фронта, треки, точки) | `data/` | GeoJSON |
| Скрипты подготовки данных и сборки | `tools/` | Python / Node |

Правило: **исходник не копируется в проект**. В проекте лежит только md-производная, всегда с указанием, из какого файла в Obsidian она получена.

## Соглашения для md-производных

Файл: `docs/sources/<ГГГГ-ММ-ДД>_<КраткоеНазвание>.md` (дата = дата документа, не дата распознавания).
Один документ = один файл. Страницы разделяются маркером `<!-- page: N -->`.

Обязательный front-matter:

```yaml
---
источник: "Хобби/365сд/Исходники/имя_файла.pdf"   # путь внутри Obsidian vault
файл: "имя_файла.pdf"                              # имя исходника
страниц: 3
язык_оригинала: de        # de | ru
перевод: полный           # нет | полный | частичный
архив: "NARA T-315 R-…"   # если известно: архив, фонд, опись, дело
дата_документа: 1942-03-?
подразделение: "365 сд"   # о ком документ
статус: черновик          # черновик | выверено
---
```

Тело: сначала распознанный текст на языке оригинала (`## Оригинал`), затем перевод (`## Перевод`) — если перевод есть. Неясные места помечать `[?]`, не додумывать. Числа, фамилии, топонимы — как в документе, без «исправлений».

## Индекс

Реестр обработанных документов — `docs/sources/README.md`: одна строка на документ (файл-производная → исходник → краткое содержание → что даёт для проекта).

## Данные боевого пути (`data/`)

Машиночитаемый набор событий и формирований. Спецификация поведения — `openspec/specs/` (после архивации change) и `openspec/changes/add-combat-path-data-model/`.

Раскладка:

- `data/schemas/` — JSON-схемы (draft 2020-12): `fact`, `event`, `unit`, `source`, `registry`
- `data/registry.json` — перечень типов событий, уровней локализации, точностей даты, статусов
- `data/sources.json` — реестр исходников: `id`, путь в Obsidian, путь к производной, `sha256`
- `data/units.json` — формирования и периоды подчинения
- `data/events/<год>.json` — события; файл = год, `year` в файле обязан совпадать с именем файла

Правила, которые проверяются машиной:

1. **Каждый факт — объект** `{value, provenance, status}`; провенанс неотделим от значения. Конфликт: `{conflict: true, variants: [...]}` — минимум два варианта, статус выверки у конфликта не ставится.
2. **Провенанс** = `source_id` из `data/sources.json` + локатор (`page` / `slide` / `paragraph` / `quote`, минимум одно поле). Путь к производной и к исходнику в реестре обязан существовать, `sha256` исходника — совпадать.
3. **Статус `выверено`** допустим только при двух разных `source_id`; два локатора одного источника независимым подтверждением не считаются.
4. **Даты** — интервал `{from, to, precision}`; `precision: day` требует одинаковых границ, `month` — целый месяц, `range` — произвольный интервал, `null` — открытая граница. Неизвестная дата — обе границы `null`, а не выдуманные числа.
5. **Геометрия** — GeoJSON в WGS84 или `null`. Без геометрии уровень локализации обязан быть `approximate`.
6. **Провенанс блокирует сборку:** при любом нарушении `tools/build.py` не пишет артефакты.

Пополнение источников и фактов — **штатная операция, отдельный OpenSpec change не требуется**: меняется содержимое `data/`, а не поведение или контракт. Change нужен, когда меняется контракт (новый вид источника, новый тип локатора, схема) или поведение инструментов.

Как добавить событие:

1. Положить исходник в Obsidian `Хобби/365сд/Исходники/`, написать производную в `docs/sources/`, внести строку в индекс.
2. Зарегистрировать источник в `data/sources.json` (для замены скана — новый `id` с версией, старый не править).
3. Дописать событие в `data/events/<год>.json` с провенансом на конкретный локатор.
4. `python3 tools/validate.py` — должно быть 0 нарушений.
5. `python3 tools/build.py` — обновит хронологию и GeoJSON.

Команды:

```bash
python3 tools/validate.py                # проверки схемы и провенанса
python3 tools/build.py                   # хронология + data/dist/features.geojson
python3 tools/build.py --check           # только сравнить артефакты с данными
python3 -m unittest discover -s tests -v # тесты валидатора и сборки
```

Корень Obsidian берётся из переменной `VOV_VAULT` (по умолчанию `~/Documents/Obsidian Vault`), переопределяется флагом `--vault`.

Артефакты: `docs/research/Боевой путь — хронология (сгенерировано).md` (не редактировать вручную) и `data/dist/features.geojson` (в git не попадает). Ручной анализ — `docs/research/Бизяев ЕМ — сводка и расхождения.md`.

## Места и геоданные

`data/places.json` — реестр мест: `id`, названия, тип, `state` (`found` | `tract` | `unfound`), `accuracy` (`exact` | `settlement` | `district` | `approximate`), `region` для запросов, `coords` как факт (`{value: {lon, lat}, provenance, status}`) или `null`.

Правила:

1. Координата без провенанса не принимается; провенанс геоданных обязан вести на запись журнала `geo-<slug>` в `docs/sources/недат_Геокодирование Nominatim — журнал запросов.md` и на файл кэша `data/cache/geocode/<slug>.json`.
2. `found` и `tract` требуют координат, `unfound` — наоборот, их не имеет и не должен иметь. Событие может ссылаться на `unfound`-место: тогда оно остаётся в хронологии с пометкой «место не локализовано» и не попадает в GeoJSON.
3. Координаты — WGS84 в порядке «долгота, широта»; выход за `bbox` из `data/registry.json` (район проекта) считается ошибкой — так ловятся перепутанные широта и долгота и одноимённые селения в других регионах.
4. Кандидат геокодера принимается только при совпадении названия **и** района/области. «Малая Борщевка» — не «Борщёвка»; такие двойники попадают в реестр вручную через `names.alternate`, а не автоматически.
5. Событие, у которого есть и своя геометрия, и место, использует свою геометрию; иначе берётся точка места, а уровень локализации — из `accuracy` места.

Как добавить место:

1. Дописать запись в `data/places.json` (`state: unfound`, `coords: null`, `region` с районом и областью).
2. `python3 tools/geocode.py --all` — заполняет кэш из Nominatim (не чаще 1 запроса в секунду).
3. `python3 tools/geocode.py --all --apply` — переносит принятые кандидаты в реестр и перегенерирует журнал.
4. `python3 tools/validate.py` — проверить цепь провенанса.

Атрибуция и ограничения: координаты — OpenStreetMap / Nominatim, данные © OpenStreetMap contributors, ODbL 1.0. Запросы ограничены одним в секунду и имеют собственный User-Agent. Ответы кэшируются в `data/cache/geocode/` и коммитятся: проверки и сборка работают офлайн, `tools/validate.py` и `tools/build.py` в сеть не ходят вовсе.

```bash
python3 tools/geocode.py --all              # дозаполнить кэш (сеть)
python3 tools/geocode.py --all --offline    # только кэш
python3 tools/geocode.py --all --apply      # применить к data/places.json
python3 tools/geocode.py --journal-only     # перегенерировать журнал
```

## Веб-источники

Сайты и форумы регистрируются видом `website` — только со снимком. Снимок лежит в `data/cache/<site>/<ГГГГ-ММ-ДД>/`: по файлу на страницу плюс карта `pages.json` (`URL → файл`, отсортирована по URL). Прошлые снимки не перезаписываются, поэтому старые цитаты остаются воспроизводимыми, даже если страница на сайте исчезла.

Правила:

1. Факт с веб-источника обязан иметь в локаторе `url` конкретной страницы; корень сайта не принимается, адрес должен разрешаться в карту снимка.
2. Источник, чей текст скопирован из другого источника реестра, обязан указать это в `derived_from`. Источники, связанные этой связью (в любую сторону, транзитивно), считаются **одной линией передачи** и не дают второго независимого подтверждения: статус «выверено» на паре «сайт + его перепечатка» отклоняется с объяснением.
3. Сети требует только снимок. `tools/validate.py` и `tools/build.py` работают офлайн по карте и файлам снимка.

```bash
# снять сайт (вежливо: 1 запрос/сек, свой User-Agent)
python3 tools/snapshot_site.py --start https://365sd.org/ \
    --cache data/cache/site-365sd --date 2026-11-25 --limit 300

# одна страница с параметрами (форум)
python3 tools/snapshot_site.py --allow-query --limit 1 \
    --start "http://www.polk.ru/forum/index.php?showtopic=2617" \
    --cache data/cache/polk-2617 --date 2026-11-25

# сравнить сайт с текущим снимком, ничего не записывая
python3 tools/snapshot_site.py --check --start https://365sd.org/ --cache data/cache/site-365sd
```

Порядок добавления веб-источника: снять снимок → сохранить главную страницу в Obsidian (как получено) и посчитать sha256 → зарегистрировать источник (`kind: website`, `snapshot_at`, `cache_path`, `vault_path`, `sha256`) → написать разбор в `docs/sources/` → проставить `derived_from`, если текст перепечатан откуда-то → проставить факты с `url`-локаторами → `python3 tools/validate.py`.

## Документы и люди

`data/documents.json` — архивные документы: `type` из `document_types`, дата как период-факт, `requisites` (только полные: `fund`, `inventory`, `file`, опционально `sheets`, либо `null` с обязательным примечанием), `carrier` (чем документ опубликован: `source_id` + `url` страницы снимка либо путь к производной).

`data/people.json` — персоны: `id`, ФИО в написании источника, `birth_year` числом или строкой `"неизвестен"`. `data/rosters.json` — записи именных списков: `document`, `person`, `unit`, `fate` (из `fate_outcomes`), `fate_date`, `facts` (партийность, состав, ВУС, примечания).

Правила:

1. Реквизиты не бывают частичными: «фонд есть, описи нет» отклоняется. Нет реквизитов — `null` и примечание, почему.
2. Документ обязан иметь носитель; `url` носителя должен разрешаться в снимок источника.
3. Событие может перечислять `documents`; в сгенерированной хронологии под событием печатается тип, дата и реквизиты или «реквизиты не установлены».
4. Запись списка всегда ссылается на документ и персону. Судьба без ссылки на список не принимается.
5. Дубли персон ловятся по нормализованным ФИО + году рождения. Однофамильцы с разными годами — не дубли.
6. Если два списка дают разные сведения об одном человеке, обе записи остаются, а персона помечается `conflict: true`. Флаг без расхождений — ошибка, расхождение без флага — тоже.

Утверждения о человеке (`claims`):

```json
"claims": {
  "birth_year": [{"value": 1913, "basis": "memorial-card", "status": "черновик",
                  "provenance": {"source_id": "src-365sd-org", "locator": {"url": "…", "quote": "…"}}}],
  "fate": [{"value": "погиб при освобождении д. Полуханово и Голяди", "basis": "memorial-card", …}]
}
```

- Ключ утверждения — из `person_fact_keys`; значение — массив свидетельств, а не одно значение: два источника о годе рождения не перетирают друг друга.
- `basis` (вид свидетельства) обязателен: архивный документ, публикация, мемориальная карточка, презентация, музейный экспонат, форум, устное свидетельство. Ставится на утверждение, а не на источник.
- Персона живёт без записи списка, но персона без записей и без утверждений — ошибка.
- Расхождение значений одного утверждения обязывает поставить `"conflict": true`; флаг без расхождений — тоже ошибка.

Реквизиты документа бывают двух полных видов: архивные (`fund`, `inventory`, `file`, опционально `sheets`) и публикационные (`edition`, `volume`, `page`, опционально `entry`). Смешивать виды нельзя, частичные наборы не принимаются.

### Архивный портал

Источник вида `archive-portal` описывается каталогом выгрузки, а не снимком страниц: поля `portal`, `cache_path` (внутри — `catalogue.json`), `fetched_at`, `query`. Такой источник:

- не требует `vault_path` и `sha256` (файлов много, они живут в Obsidian);
- проверяется на наличие каталога, адреса портала, даты выгрузки и запроса отбора;
- отдаёт документы через носитель `portal_url` + `portal_id` + `file_path` + `bytes`.

Внесение документов — инструментом, не руками:

```bash
python3 tools/portal_intake.py --source src-pamyat-naroda --dry-run   # посмотреть, что добавится
python3 tools/portal_intake.py --source src-pamyat-naroda             # внести
python3 tools/validate.py            # проверка: файл существует, размер сходится с каталогом
python3 tools/validate.py --deep     # сверка sha256 (долго: сотни мегабайт)
```

Разбор идемпотентен: повторный прогон печатает «добавлено 0, уже были N». Тип карточки портала переводится по таблице `portal_types` реестра; неизвестный тип — ошибка разбора, а не «other по умолчанию». Реквизиты выводятся из идентификатора дела (`208-0002511-0275` → ф. 208, оп. 2511, д. 275) и в примечании документа прямо сказано, что они выведены из пути, а не прочитаны с титульного листа.

Документы без сканов не вносятся: они остаются в `archive_order` каталога и в списке на заказ.

Разбор табличного списка (полуавтоматический):

```bash
# 1. черновик + отчёт, в данные ничего не пишется
python3 tools/parse_roster.py --cache data/cache/site-365sd \
    --url "https://365sd.org/imennoy-spisok-na-komandu-1213-sp-otravlya/" \
    --document doc-name-list-1213-1941-08-27 --unit 1213sp --source src-365sd-org

# 2. посмотреть data/drafts/<slug>.json и отчёт, затем применить
python3 tools/parse_roster.py ... --apply

python3 tools/validate.py
```

Черновик не попадает в данные автоматически: в списках бывают пустые строки и слитые ячейки, а ошибка разбора превращается в ложную судьбу человека. Отчёт печатает число строк, принятых записей, строк без ФИО, пустых ячеек и нераспознанных колонок.

## Линия фронта

Линия фронта — полилиния на дату, снятая с конкретного листа карты:

- `data/front_lines/1941.json` — записи `fl-ГГГГ-ММ-ДД`: дата-факт, `geometry` (LineString в WGS84), `accuracy_km`, `accuracy_level` из реестра, провенанс на лист (`sheet`, `sheet_date`) и `traced_by`.
- Дата линии обязана совпадать с датой листа-основания — иначе проверка отклоняет запись.
- Точность обязательна: лист 1:1 000 000 не может давать лучше ±5 км. Это проверяется, а не подразумевается.
- Точки обязаны попадать в границы театра (`front_bbox` реестра), дубли соседних точек и самопересечения — ошибки.
- Если событие на ту же дату оказывается дальше 25 км от линии, валидатор печатает **предупреждение** с расстоянием: повод разобраться, а не автоправка.

Сборка выдаёт `data/dist/front_lines.geojson` и `data/dist/frames.json` (дата → линия, точность, события на эту дату) — плееру не нужно угадывать порядок кадров.

Оцифровка: `tools/trace_front_line.html` — открыть в браузере, загрузить скан листа, добавить калибровочные точки на известные города (координаты есть в `data/places.json`) и обвести линию. Управление: колесо — масштаб к курсору, протяжка левой кнопкой (или правая кнопка / пробел+протяжка) — панорама, `0` — вписать лист, `+`/`-` — масштаб; короткий клик ставит точку. Экспорт даёт JSON, который переводится в координаты:

- **две точки** — подобие (сдвиг, поворот, масштаб), 4 параметра;
- **три и больше** — аффинная подгонка по наименьшим квадратам: используются все точки, компенсируется перекос скана, а по остаткам видно, какая подпись опознана неверно (инструмент сам называет худшую точку).

Практика: для полосы Клин — Калинин — Ржев мало двух дальних якорей, лучше 3–6 точек вокруг интересующего района. Но точность линии всё равно ограничена масштабом листа: 1:1 000 000 даёт ±5–10 км, и никакая калибровка этого не отменит — поэтому линия хранится с обязательным `accuracy_km`.

```bash
python3 tools/front_line_trace.py --input pixels.json --date 1941-12-06 \
    --sheet ca000124 --sheet-date 1941-12-06 --accuracy-km 10
```

Калибровка, снятая с листа `ca000124` (Клин, Калинин, Ржев), лежит в `data/calibration/lage-ost-ca000124.json` — её можно загрузить в инструмент кнопкой «загрузить JSON» и продолжить обводку.

Автотрейс по цвету (`tools/front_line_extract.py`) на листах Lage Ost **не работает и не должен использоваться**: линия фронта нанесена тёмно-синим, но тем же тёмно-синим подписаны номера немецких соединений и значки, поэтому маска ловит подписи, а не фронт (проверено на листе 6.12.1941 — наложенная ломаная прыгает по «XXVII.m.», «5.Pz.», «44.R.»). Скрипт оставлен как заготовка для листов другой серии и без флага `--accept` пишет только черновик и предупреждение.

## Правило работы: ядро и контент

Проект разделён на две части, и они коммитятся по-разному:

| Что | Где | Как попадает в мастер |
|---|---|---|
| **Ядро** — инструмент | `tools/*.py`, `tools/*.html`, `tools/install_hooks.sh` | отдельной веткой, слияние **одновременно со сменой версии ядра** |
| **Версия и история** | `tools/VERSION`, `tools/CHANGELOG.md` | вместе со слиянием ядра |
| **Контент** — данные и документы | `data/**`, `docs/**`, `openspec/**`, `README.md` | прямо в мастер, без ветки |

Версия ядра — semver в `tools/VERSION`, читается всеми инструментами через `tools/coremeta.py`. Она печатается валидатором (`ядро 1.0.0`) и вписывается в каждый сгенерированный артефакт: `build.py --check` считает артефакт, собранный другой версией, расхождением — то есть смена ядра обязывает пересобрать выход.

Релиз ядра:

```bash
git checkout -b feature/<что-делаем>       # работа над инструментом — в ветке
python3 tools/release_core.py --bump minor # поднять версию и завести запись в CHANGELOG
# заполнить перечень изменений в tools/CHANGELOG.md
git add -A && git commit -m "ядро 1.1.0: ..."
git checkout master && git merge --no-ff feature/<что-делаем>
python3 tools/build.py && python3 tools/build.py --check
git push github master && git push gitverse master
```

Правило защищено хуком: `sh tools/install_hooks.sh` ставит pre-commit, который отказывает в коммите, если меняется ядро, а `tools/VERSION` — нет. Проверка перед слиянием: `python3 tools/guard_core.py --merge-base master`. Обход `--no-verify` возможен, но `build.py --check` ловит его по версии в артефактах.

## OpenSpec

```bash
openspec list                                     # активные change
openspec validate add-combat-path-data-model --strict
openspec archive add-combat-path-data-model       # после выполнения задач
```

Важные изменения — только через change: proposal → specs → design → tasks → apply.

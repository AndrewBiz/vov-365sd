# source-intake Specification

## Purpose

Принимает веб-источники так же строго, как архивные документы: со снимком, картой страниц, адресуемыми цитатами и явной фиксацией того, какой источник произведён от какого.

## Requirements

### Requirement: Веб-источник регистрируется только со снимком

Источник вида `website` SHALL иметь дату снимка, каталог выгрузки и карту `URL → файл`. Источник без снимка не регистрируется.

#### Scenario: Сайт без даты снимка
- **WHEN** в реестр добавляется источник вида `website` без даты снимка
- **THEN** проверка отклоняет источник и сообщает, какое поле отсутствует

#### Scenario: Каталог выгрузки не найден
- **WHEN** каталог снимка, указанный у источника, отсутствует в репозитории
- **THEN** проверка сообщает об отсутствии снимка и называет ожидаемый путь

### Requirement: Цитата с веб-источника ссылается на конкретную страницу снимка

Локатор факта, взятого с веб-источника, SHALL содержать `url`, и этот адрес SHALL разрешаться в файл внутри снимка. Цитата без конкретного адреса не принимается.

#### Scenario: Указан домен вместо страницы
- **WHEN** локатор веб-источника содержит только корневой адрес сайта
- **THEN** проверка отклоняет факт как неадресуемую цитату

#### Scenario: Страница исчезла из снимка
- **WHEN** `url` не разрешается в файл снимка
- **THEN** проверка сообщает, какой адрес не найден, и предлагает обновить снимок

### Requirement: Карта страниц снимка детерминирована

Снимок SHALL содержать карту `URL → файл`, отсортированную по URL, и по одному файлу на страницу. Повторный обход без изменений на сайте SHALL давать ту же карту.

#### Scenario: Повторный снимок без изменений
- **WHEN** снимок снимается дважды при неизменном сайте
- **THEN** карта страниц побайтово совпадает

#### Scenario: Сайт изменился
- **WHEN** между снимками на сайте появились или исчезли страницы
- **THEN** новая карта содержит только актуальные страницы, а расхождение с предыдущим снимком доступно как список изменений

### Requirement: Производность источников фиксируется явно

Источник, текстом которого является другой источник (перепечатка, компиляция, копия), SHALL указывать это в поле `derived_from` со ссылкой на исходный источник реестра.

#### Scenario: Презентация как компиляция сайта
- **WHEN** текст источника дословно повторяет другой источник реестра
- **THEN** у производного источника заполняется `derived_from`, а в примечании указывается, что именно было скопировано

#### Scenario: Ссылка на несуществующий источник
- **WHEN** `derived_from` содержит идентификатор, которого нет в реестре
- **THEN** проверка отклоняет источник и называет неизвестный идентификатор

### Requirement: Связанные источники не считаются независимыми

При проверке статуса «выверено» источники, соединённые связью `derived_from` в любую сторону и транзитивно, SHALL считаться одной линией передачи и не давать второго независимого подтверждения.

#### Scenario: Сайт и его перепечатка
- **WHEN** факт подтверждён сайтом и источником, у которого этот сайт указан в `derived_from`
- **THEN** проверка понижает статус до черновика и объясняет, что подтверждение одно

#### Scenario: Независимое подтверждение
- **WHEN** факт подтверждён двумя источниками без связи `derived_from` между ними
- **THEN** статус «выверено» допускается

### Requirement: Снимок сохраняет разметку страниц с таблицами

Если страница снимка содержит таблицу, снимок SHALL дополнительно сохранять её HTML-разметку в `raw/<slug>.html`, а карта страниц — указывать оба файла: текст и разметку.

#### Scenario: Страница с именным списком
- **WHEN** страница содержит таблицу с колонками «№, ФИО, партийность, состав»
- **THEN** в снимке появляется HTML-файл этой страницы, а карта содержит и текстовый, и разметочный путь

#### Scenario: Страница без таблиц
- **WHEN** страница не содержит таблиц
- **THEN** HTML-файл для неё не создаётся, карта содержит только текстовый путь

#### Scenario: Сравнение снимков
- **WHEN** снимок сравнивается в режиме проверки
- **THEN** наличие или отсутствие разметки на расхождения по составу страниц не влияет

### Requirement: Входящие в хранилище — точка входа

Инструмент SHALL иметь команду обзора папки «Входящие для разбора» в хранилище, которая печатает для каждого файла размер, sha256 и признак «известен/нов» по реестру источников и документам, и SHALL NOT изменять файлы или данные при обзоре.

#### Scenario: Обзор входящих
- **WHEN** в папке входящих лежат два файла, один из которых уже зарегистрирован
- **THEN** обзор показывает оба, у известного стоит отметка «известен», у нового — предложенный slug

#### Scenario: Пустая папка
- **WHEN** папка входящих пуста или отсутствует
- **THEN** обзор сообщает об этом и не считает это ошибкой

### Requirement: Артефакт из хранилища не копируется в репозиторий

Для файлов, лежащих в хранилище, инструмент SHALL создавать артефакт инбокса, ссылающийся на путь в хранилище (`from_vault: true`), и SHALL NOT копировать содержимое в репозиторий.

#### Scenario: Крупный скан
- **WHEN** файл в хранилище больше десятков мегабайт
- **THEN** артефакт содержит путь и sha256, а байты остаются в хранилище

#### Scenario: Пропавший файл к моменту разбора
- **WHEN** файл удалён из хранилища после `adopt`
- **THEN** разбор сообщает, что файл не найден, и артефакт нельзя применить

### Requirement: Применение источника переносит файл и вносит запись

`apply` для видов-источников SHALL: сверить sha256, перенести файл из входящих в целевую папку хранилища, проверить запись по схеме и внести источник в `data/sources.json`; при нарушении схемы SHALL вернуть файл на прежнее место.

#### Scenario: Новый источник
- **WHEN** артефакт с видом `personal-letters` применён
- **THEN** файл оказывается в `Исходники/<location>/`, а в `data/sources.json` появляется источник с этим файлом и его sha256

#### Scenario: Файл падает по схеме
- **WHEN** запись источника не проходит схему
- **THEN** файл возвращается во входящие, запись не создаётся, причина пишется в журнал

#### Scenario: Дополнение существующего источника
- **WHEN** при применении указан существующий `--source-id`
- **THEN** файл добавляется в `files` этого источника, а не создаёт второй источник

### Requirement: Виды инбокса покрывают личные материалы

Перечень видов инбокса SHALL включать, кроме документов портала, виды источников личного происхождения: `personal-letters`, `museum-photo`, `archive-reply`.

#### Scenario: Письма через конвейер
- **WHEN** файл подборки писем разбирается через инбокс
- **THEN** вид `personal-letters` допустим, и `apply` вносит источник, а не документ портала

# Design

## Context

См. `proposal.md` — Why. Текущее состояние репозитория: `docs/sources/` содержит 4 распознанных документа, `docs/research/` — ручную сводку по Бизяеву Е. М.; `data/` и `tools/` пусты. OpenSpec поднят (`spec-driven`, язык артефактов ru).

Ограничения, формирующие подход:

- Корпус мал (единицы документов, десятки фактов) и будет расти неравномерно — рывками при получении архивных ответов.
- Источники противоречат друг другу (четыре даты гибели), часть реквизитов прочитана неуверенно — модель обязана хранить варианты и сомнения, а не вычищенный результат.
- Исходники лежат в Obsidian (`/home/anb/Documents/Obsidian Vault`), репозиторий их не содержит; связь — только по пути и идентификатору.
- Доступно: Python 3.14, `jsonschema` 4.26, git. Внешние сервисы и сеть для проверок не используются.

## Goals / Non-Goals

**Goals:**

- Декларативный контракт данных, проверяемый машиной, и совместимый с будущим читателем карты/таймлайна.
- Провенанс, отвязать который от факта технически невозможно.
- Хранение конфликтов как первого класса, с запретом автоматического выбора.
- Детерминированная сборка и генерация человекочитаемой сводки.
- Нулевые внешние зависимости сверх `jsonschema`.

**Non-Goals:**

- Карта, таймлайн, анимация (следующие change).
- Немецкая сторона и сравнение с документами вермахта (отдельный change).
- Импорт из «Память народа»/ОБД, любые API-интеграции.
- База данных, веб-сервис, редактирование данных через UI.

## Decisions

**1. JSON Schema 2020-12 + `jsonschema` (`Draft202012Validator`).** Контракт живёт отдельно от кода, читается человеком и другими инструментами (валидаторы IDE, генераторы форм). Альтернативы: pydantic (контракт растворяется в коде, нужна зависимость), YAML без схемы (нет строгости типов). Выбор согласуется с уже принятой в работе практикой jsonschema-контрактов.

**2. Файлы вместо БД.** `data/schemas/*.schema.json` (контракты), `data/registry.json` (типы событий, уровни локализации, типы точности дат), `data/sources.json` (реестр источников), `data/units.json` (формирования), `data/events/<год>.json` (события). Git-дифф показывает историю фактов; SQLite удобнее для запросов, но не диффится и не рецензируется.

**3. Факт — объект, а не скаляр.** Любое значение поля записывается как `{value, provenance, status}`, при конфликте — `{variants: [...], conflict: true}`. Отдельный файл провенанса или комментарий рядом отклонены: их легко рассинхронизировать, тогда как поле в том же объекте валидируется схемой.

**4. Провенанс через `source_id`, а не через путь.** `data/sources.json` хранит для каждого источника: `id`, `vault_path`, `derivative_path`, `sha256`, `kind`. Факт ссылается на `source_id` + локатор `{page?, slide?, paragraph?, quote?}`; хотя бы одно из полей локатора обязательно. Это даёт: обнаружение переименования (путь), обнаружение подмены содержимого (sha256), отсутствие дублирования длинных путей в каждом факте. Альтернатива — путь в каждом факте: рассинхронизация при переименовании и раздувание файлов.

**5. Замена скана = новый источник, а не правка старого.** Если файл в Obsidian легитимно заменён (пересъёмка, другой скан), заводится `source_id` с суффиксом версии; факты старого источника остаются. Иначе sha256-проверка превращается в вечную ручную работу.

**6. Даты: интервал + точность.** `period: {from, to}` (ISO 8601, любая граница может быть `null`) и `precision: day | month | year | range`. «Август 1942» — это `1942-08-01…1942-08-31` с `precision: month`; открытый интервал — `to: null` и `precision: range`. Строки вида «примерно» не допускаются: неопределённость живёт в структуре.

**7. Конфликт не разрешается кодом.** Сохранение варианта с `conflict: true`; статус «выверено» схема запрещает при `conflict: true`, а валидатор требует ≥2 независимых источников. Выбор версии человеком выражается добавлением факта-решения с отдельным провенансом и ссылкой на обоснование — так решение тоже проверяемо.

**8. Геометрия внутри события, экспорт — артефакт сборки.** Событие может содержать GeoJSON-объект (WGS84) и `localization: exact | settlement | district | approximate`. Сборка формирует `data/dist/features.geojson` (FeatureCollection) — это то, что будет читать карта; сам каталог `dist/` в git не попадает.

**9. Валидатор — отдельный скрипт, два уровня проверок.** `tools/validate.py`: (а) схема JSON Schema; (б) семантика — уникальность id, ссылочная целостность юнитов и источников, существование производной и исходника, совпадение sha256, наличие локатора, геометрия без уровня локализации, конфликт без вариантов, «выверено» без двух источников. Код возврата ≠ 0 при любой ошибке: проверки блокируют публикацию, как требует спека.

**10. Сборка детерминирована и идемпотентна.** `tools/build.py` сортирует по `id`, склеивает годы, пишет сводку и FeatureCollection; повторный запуск сравнивает хеш результата с предыдущим и падает при расхождении. Сводка помечается «сгенерировано, не редактировать вручную» и содержит хеш исходных данных.

**11. Ручная сводка не заменяется.** `docs/research/Бизяев ЕМ — сводка и расхождения.md` остаётся аналитическим текстом; из данных генерируется отдельный файл `docs/research/Боевой путь — хронология (сгенерировано).md`. Смешивать ручной анализ и генерацию в одном файле нельзя — иначе перезапись уничтожит рассуждения.

**12. Тип события `source-gap`.** Отрицательные ответы архива («не значится в документах») моделируются как событие с типом `source-gap`, а не как отсутствие данных: так они видны на таймлайне и попадают в сводку.

## Risks / Trade-offs

- [Файлы данных станут шумными в диффах при росте корпуса] → группировка событий по годам; при превышении разумного размера — разбиение по соединениям.
- [sha256 ломается при каждом пересъёме] → правило версионирования `source_id` (решение 5) и явная команда пере-регистрации источника.
- [Двойной учёт: факт есть и в производной md, и в JSON] → единственный источник истины для сборки — JSON; md остаются транскрипцией, их расхождение с JSON ловится обзором, но не блокирует сборку.
- [Оверинжиниринг на корпусе из четырёх документов] → минимальный набор обязательных полей, расширение только при появлении реального источника.
- [Свободные текстовые `value` не сравнить автоматически] → конфликт детектируется человеком и помечается явно; автодетект расхождений не заявляется как поведение системы.

## Migration Plan

1. Создать `data/schemas/`, `data/registry.json`, `data/sources.json` с четырьмя существующими источниками (id, путь в vault, путь к производной, sha256).
2. Внести `data/units.json`: 365 сд, 1211/1213/1215 сп, 927 ап, 379 сд, 30 А, 29 А.
3. Внести `data/events/1941.json` и `1942.json`: формирование дивизии, Кинешма, Дмитров, Клин, Вьюхово, Лотошинский район, Калицино/Дьяково (24.12.1941–10.01.1942), окружение 29 А, прорыв 17.02.1942, судьба Бизяева Е. М. как конфликт из четырёх вариантов.
4. Прогнать `tools/validate.py` и `tools/build.py`, получить сводку и FeatureCollection.
5. Сверить сгенерированную хронологию с ручной сводкой; расхождения — либо ошибка внесения, либо новый конфликт.

Откат: change затрагивает только новые каталоги и файлы; удаление `data/` и `tools/` возвращает репозиторий в текущее состояние, производные и исходники не затрагиваются.

## Open Questions

- Перечень типов событий для немецкой стороны (боевые донесения, приказы, разведсводки) — определится при появлении источника, до тех пор реестр расширяется без изменения схемы.
- Нужно ли хранить текстовые цитаты (`quote`) целиком в данных или достаточно локатора — решится, когда объём цитат начнёт дублировать производные; поле в схеме уже предусмотрено как опциональное.

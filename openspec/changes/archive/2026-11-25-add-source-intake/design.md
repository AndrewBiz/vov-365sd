# Design

## Context

См. `proposal.md` — Why. Текущее состояние: 7 источников в `data/sources.json`, два из них веб (сайт 365sd.org с выгрузкой 142 страниц в `data/cache/site-365sd/`, форум polk.ru), оба записаны как `kind: "other"`; локатор факта знает только `page/slide/paragraph/quote`, поэтому цитаты с сайта висят на `paragraph: "страница «Состав»…"`.

Ограничения:

- Проверки и сборка работают офлайн; сеть допустима только в инструменте снимка (как в геокодировании).
- Сайты меняются: снимок обязан быть версионируемым, а не «тем, что было в браузере».
- Объём снимка сайта — сотни страниц; в репозитории это около мегабайта текста, что сопоставимо с кэшем геокодирования.
- Существующие архивные источники уже покрыты требованиями `source-provenance`; их трогать не нужно.

## Goals / Non-Goals

**Goals:**

- Вид источника «сайт» со снимком, датой и картой страниц.
- URL как полноценный локатор факта.
- Явная производность источников и правило «связанные источники — одно свидетельство».
- Детерминированный, офлайновый по последствиям снимок и проверки.

**Non-Goals:**

- Парсинг конкретных сайтов в структурированные сущности (биографии, именные списки) — это отдельные change про персоналии и списки.
- Автоматическая проверка «текст источника дословно повторяет другой» — производность заявляется человеком, а не детектируется машиной.
- Хранение картинок и сканов со страниц сайта: снимок — текстовый.
- Изменение требований к архивным источникам.

## Decisions

**1. Снимок — текстовая выгрузка плюс карта `URL → файл`, а не MHTML/WARC.** MHTML/WARC точнее по форме, но не диффится, весит в разы больше и не нужен: цитаты всё равно берутся из текста. Карта страниц лежит отдельным JSON, отсортированным по URL — это даёт побайтовую идемпотентность и читаемый diff между снимками.

**2. Карта страниц — единственный источник адресации.** Валидатор не ходит в сеть и не разбирает имена файлов: он читает карту из каталога снимка. Поэтому смена схемы URL на сайте не ломает проверки старых цитат — старые страницы остаются файлами в старом снимке.

**3. Локатор `url` — добавление поля, а не новый тип локатора.** Схема локатора расширяется полем `url` с форматом адреса; правило «минимум одно поле» сохраняется. Альтернатива — отдельный тип «веб-локатор» — потребовала бы ветвления во всех проверках и не даёт ничего, кроме строгости вида.

**4. Версия снимка — каталог с датой.** `data/cache/<site>/<YYYY-MM-DD>/` + указатель `current` в реестре источника (`snapshot_at`). Обновление снимка = новая дата и новый каталог; прошлый остаётся, пока на него ссылаются цитаты. Это дороже, чем «перезаписать», но именно так работает требование воспроизводимости: цитата 2026 года должна разрешаться и в 2028-м.

**5. Производность объявляется человеком.** Поле `derived_from` заполняется вручную при разборе; машина проверяет только то, что источник существует и что связи нет в цепочке подтверждений. Автодетект «этот текст скопирован оттуда» (шинглы, косинус) отвергнут: ошибки такого детекта создают ложные понижения статусов там, где нужно доверие к источнику.

**6. Независимость — транзитивное замыкание по `derived_from`.** Два источника независимы, если между ними нет пути по `derived_from` ни в одну сторону. Проверка простая (обход в ширину), но закрывает основной практический случай: сайт → презентация → пересказ в книге.

**7. Инструмент снимка — отдельный, как геокодер.** `tools/snapshot_site.py`: обход в ширину от стартовых страниц, ограничение частоты, User-Agent, сохранение текста и карты, режим `--check` (сравнить с текущим снимком без записи). Сеть только здесь; `validate`/`build` остаются офлайновыми.

**8. Отказ от индексации через sitemap.** У 365sd.org нет ни sitemap, ни REST API — обход строится по внутренним ссылкам с ограничением глубины и количества. Это зафиксировано как штатное поведение: инструмент принимает список стартовых URL и лимит страниц, а полноту обхода подтверждает человек, глядя на карту.

## Risks / Trade-offs

- [Снимок в git растёт] → текст, а не MHTML; один мегабайт на сайт; при росте — вынос старых версий в архивные каталоги.
- [Человек забудет заполнить `derived_from`] → проверка не может это поймать; митигация — правило в README и явный пункт в чек-листе разбора источника.
- [Ложная независимость при двух сайтах-перепечатках] → связи между сайтами тоже объявляются вручную; при появлении третьего перепечатки — отдельный разбор.
- [Сайт закрылся или сменил адрес] → снимок в репозитории остаётся действительным источником; `url` продолжает разрешаться в файл, даже если в сети страницы уже нет.
- [Неполный обход (лимит страниц)] → карта показывает фактически снятое; в примечании источника фиксируется лимит, чтобы «нет упоминания» не принимали за доказательство отсутствия.

## Migration Plan

1. Расширить `source.schema.json` (вид `website`, `snapshot_at`, `cache_path`, `derived_from`) и `fact.schema.json` (поле `url` в локаторе).
2. Перевести `src-365sd-org` и `src-polk-forum-2617` на вид `website`, добавить `snapshot_at` и карты страниц; форум сохранить как одностраничный снимок.
3. Проставить `src-pptx-365.derived_from = ["src-365sd-org"]` с примечанием, что именно скопировано.
4. Переписать локаторы существующих цитат с сайта на `url`; факты, где вместо адреса стоял `paragraph`, привести к виду «url + цитата».
5. Реализовать `tools/snapshot_site.py`, проверки независимости, тесты (включая сценарий «сайт + его перепечатка»).
6. Обновить README и индекс производных.

Откат: поля схемы аддитивны, старые данные без `url` и `derived_from` остаются валидными до миграции шага 4; откат — `git revert`.

## Open Questions

- Нужен ли режим сравнения двух снимков как отдельный вывод (`--diff`) или достаточно `git diff` по каталогам — решится на практике после второго снимка.
- Хранить ли тексты страниц с разметкой абзацев для цитат подлиннее — сейчас сохраняется чистый текст.

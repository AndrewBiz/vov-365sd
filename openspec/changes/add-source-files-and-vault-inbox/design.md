# Design

## Контракт источника: список файлов

```jsonc
{
  "id": "src-bizyaev-letters-1941",
  "kind": "personal-letters",
  "title": "Письма с фронта Бизяева Е. М. (август–декабрь 1941) и справка племянника",
  "derivative_path": "docs/sources/1941-08-04_Письма с фронта Бизяева ЕМ (август-декабрь 1941).md",
  "files": [
    { "path": "Хобби/365сд/Исходники/Письма Бизяева Е.М. (1941)/letters-from-war-1941 v2_1-1.pdf",
      "sha256": "7119a0…", "role": "transcription" },
    { "path": "…/letters-from-war-1941 v2_1-2.pdf", "sha256": "…", "role": "scans" },
    { "path": "…/letters-from-war-1941 v2_1-3.pdf", "sha256": "45d5df…", "role": "photos" }
  ],
  "received": "2026-11-26"
}
```

Почему массив, а не «дополнительные файлы»: у подборки нет «главного» файла. Роль (`role`) говорит, что именно в файле — расшифровка, сканы, фотографии, справка; по ней отчёт и человек понимают, что открыть. Обязательны только `path` и `sha256`: роль полезна, но её отсутствие не должно мешать завести источник.

`vault_path`/`sha256` удаляются без периода совместимости: реестр маленький (10 источников), миграция механическая, а держать две формы — значит навсегда получить два пути проверки и рано или поздно разойтись.

## Проверки

- минимум один файл; `path` непустой; `sha256` — 64 hex;
- каждый файл существует в хранилище, sha256 совпадает;
- дубли внутри одного источника по `path` — ошибка (дважды один файл не считается двумя частями);
- файл, указанный в двух разных источниках, — предупреждение, не ошибка: бывает, что фрагмент входит в две подборки; решение остаётся за человеком.

## Входящие в хранилище

```
Хобби/365сд/
├── Входящие для разбора/          ← сюда кладут файлы; отсюда их забирает инструмент
└── Исходники/
    ├── ЦАМО — Память народа/…     ← сканы портала
    ├── Письма Бизяева Е.М. (1941)/
    └── Книги и презентации/
```

Папка входящих — не «свалка», а staging с обязательным сроком: файл лежит там, пока не разобран. `apply` переносит его в целевую папку, поэтому входящие сами очищаются.

`inbox` — только чтение: печатает таблицу «файл, размер, sha256 (12 знаков), известно/ново, предложенный slug». Ничего не двигает и не пишет в данные.

## Манифест артефакта из хранилища

`adopt` создаёт обычный `inbox/<slug>/artifact.yaml`, но вместо копии файла в репозиторий пишет:

```yaml
files:
  - path: "Хобби/365сд/Входящие для разбора/letters-1-2.pdf"
    sha256: "…"
    role: scans
from_vault: true
```

Так крупные PDF не дублируются в репозитории, а `scan` и `apply` знают, где брать байты. Для документов портала остаётся прежний режим: файл копируется в `inbox/<slug>/files/` и оттуда едет в хранилище.

## apply для источника

1. Взять манифест, найти файл (в хранилище или в инбоксе репозитория).
2. Проверить, что sha256 совпадает с манифестом.
3. Если включён `--source-id` и такой источник уже есть — это не ошибка: файл **добавляется** к существующему источнику (роль из манифеста), при совпадении `path` — «уже есть».
4. Иначе собрать запись источника по схеме, проверить её, затем перенести файл в `Исходники/<location>/` (move, не copy), пересчитать sha256 после переноса.
5. Любая ошибка до записи в `data/sources.json` — файл возвращается на место. Ошибка после переноса — откат переноса и запись в журнал.

Порядок «сначала проверка схемы, потом перенос» выбран потому, что провалившаяся запись не должна оставлять файл в целевой папке: иначе входящие пустеют, а реестр молчит.

## Обратная совместимость

`validate.py` и `build.py` правятся в одном месте каждый; тесты получают синтетический источник с двумя файлами. Старые артефакты инбокса (`pn-354-10-l295`, `pn-354-10-l458`) продолжают работать: их манифесты ссылаются на файлы в репозитории, `from_vault` отсутствует.

## Риски

- **Перенос вместо копии.** Если человек ждёт файл там, где положил, он его не найдёт. Смягчение: `inbox` печатает, куда файл уедет, а `apply` — итоговый путь; это же пишется в журнал.
- **Дубли по sha256 между подборками.** Один и тот же лист может попасть в две подборки; поэтому «файл в двух источниках» — предупреждение, а не отказ.

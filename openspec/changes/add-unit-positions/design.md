# Design

## Что моделируем

Не «фронт», а **состояние части**: кто, где, когда, по какому документу. Всё остальное — производное.

```jsonc
{
  "id": "pos-1941-12-11-0900-1213sp-a",
  "unit": "1213sp",
  "as_of": { "date": "1941-12-11", "time": "09:00", "precision": "timestamp" },
  "kind": "sector",
  "geometry": { "type": "LineString", "coordinates": [[36.71, 56.30], [36.75, 56.31]] },
  "label": "по состоянию на 9:00 11.12.1941",
  "sheet": {
    "source_id": "src-rkka-o-36-1941",
    "locator": { "page": 1, "quote": "по состоянию на 9:00 11.12.1941" },
    "colour": "красный",
    "legend": "сплошная красная линия — передний край на 9:00 11.12"
  },
  "basis": "map",
  "accuracy_m": 250,
  "status": "черновик"
}
```

## Решения

### Полоса — основной вид геометрии

Обводить отрезок по оригиналу проще, чем выбирать точку: на карте нет «точки части», есть линия соприкосновения, окоп, рубеж. Поэтому `sector` (LineString) — вид по умолчанию. `cp` (точка) остаётся для КП и штабов, `area` — для районов сосредоточения, `route` — для маршрутов, `line` — для случаев, когда нарисована именно линия без «полосности» (например, рубеж регулирования).

Ключевое: **геометрия не додумывается**. Если на листе нарисована только стрелка наступления — это `route` со стрелкой, а не полоса обороны.

### Время

`as_of` = `date` + `time` + `precision`:

- `timestamp` — есть и дата, и время (обычный случай для километровок);
- `day` — только дата;
- `range` — «в ночь на 12.12», интервал, `time` пустое.

`time` — строка `HH:MM` в 24-часовом формате, без часового пояса: документы писали местное время, и приводить его к UTC значит выдумывать. В отчётах время печатается как в документе.

### Базис наблюдения

- `map` — снято с карты (наш основной случай);
- `text` — названо в сводке, донесении, ЖБД («1211 сп сосредоточился в районе Воловиково»);
- `map+text` — совпадает в обоих.

Текстовое наблюдение получает `accuracy_m` выше (по умолчанию 2000 м) и `kind: cp` или `area`, потому что в тексте обычно пункт, а не рубеж. Это не «костыль для интерполяции»: это равноправный факт, просто менее точный. Интерполяция потом использует все наблюдения подряд — и карты, и тексты.

### Почему интерполяция не хранится в данных

Расчётная точка не имеет источника: её нельзя проверить, нельзя предъявить архиву, и через месяц никто не отличит её от нанесённой на карту. Поэтому:

- `data/positions/*.json` — только наблюдения;
- `data/dist/trajectories.geojson` и кадры анимации — производные, каждая вершина помечена `derived: true`, `between: ["pos-…", "pos-…"]`, `method: "linear"`, `speed_km_day`;
- в отчётах и в интерфейсе расчётный участок рисуется **пунктиром** и отключается переключателем «показывать расчётные положения».

### Правдоподобие перемещения

Скорость берётся из реестра `movement_rates` (км/сутки, верхняя граница):

| Тип | Верхняя скорость |
|---|---|
| пехота пешим порядком | 30 |
| лыжники | 40 |
| конница | 60 |
| автотранспорт | 120 |
| железная дорога | 300 |

Правила расчёта:

1. Интерполируются только **соседние по времени** наблюдения одного формирования.
2. Если расстояние / время > верхней скорости типа — сегмент **не интерполируется**: в анимации часть «перескакивает», в отчёте появляется предупреждение «перемещение неправдоподобно быстро: 62 км за 8 ч».
3. Если между наблюдениями больше 10 суток — интерполяция не выполняется (слишком много неизвестного), показывается разрыв.
4. Линия интерполяции — прямая между центрами геометрий (центроид полосы, точка КП). Огибание дорог и рельефа не моделируется: это была бы вторая выдумка поверх первой.
5. Направление не «сглаживается»: если часть шла зигзагом, между двумя наблюдениями всё равно прямая — и это честно помечено как расчёт.

### Связь с `front_lines`

`front_lines` остаётся для документов, где фронт нарисован одной линией (Lage Ost 1:1M, схемы штабов армий). Из `positions` он **не собирается**: склейка нарезок разных дивизий в общую линию — синтез, а не источник. Это правило попадает в спеку, чтобы через полгода никто не «улучшил» систему обратным путём.

### Анимация

Кадр = момент времени. Для каждого формирования:

- есть наблюдение на этот момент → сплошная геометрия, подпись с временем из документа;
- момент между наблюдениями → расчётная точка/полоса пунктиром, подпись «расчёт между 10.12 и 15.12»;
- разрыв (нет интерполяции) → часть не рисуется, в списке «нет данных».

Плавность обеспечивается частотой кадров, а не подменой фактов: шаг кадра 6 часов (или 1 час при плотных наблюдениях), при этом в кадр попадают только те положения, которые либо наблюдались, либо помечены расчётными.

### Что делать с существующим change `add-front-line-model`

Задачи про оцифровку линий 1:1M остаются в силе для Lage Ost, но приоритет ниже: главный слой теперь `positions`. Отдельного «переписывания» не нужно — достаточно, чтобы `front_lines` не разрастался искусственно.

## Риски

- **Соблазн «доиграть» анимацию.** Красивая плавная линия читается как факт. Смягчение: пунктир, переключатель, подпись «расчёт», предупреждения о неправдоподобных скоростях и запрет хранить расчётные точки в данных.
- **Полосы сложнее обводить, чем точки.** Нужен удобный инструмент обводки по скану — существующий `tools/trace_front_line.html` придётся расширить (слои, несколько полос, цвет, привязка к части и времени).
- **Текстовые сводки дают пункты, а не рубежи.** В анимации точка КП и полоса обороны визуально несопоставимы; в кадре это различается видом геометрии, а не «доводкой» до линии.

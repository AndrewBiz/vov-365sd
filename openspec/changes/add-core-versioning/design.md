# Design

## Контекст

`tools/` — девять скриптов (валидатор, сборка, парсер списков, OCR, геокодер, трейсер, автотрейс, приёмник портала, снимок сайта) и три HTML-инструмента. Данные и производные — `data/**` и `docs/**`. До сих пор всё лежало в одной истории: коммит `53356f7` одновременно меняет события и добавляет `tools/ocr_scan.py`, и по нему нельзя понять, каким ядром собрана хронология.

Правило пользователя:

1. изменение инструмента — в отдельной ветке, слияние в мастер одновременно со сменой версии ядра;
2. у ядра есть версия;
3. контент (данные) коммитится в мастер.

## Решения

### Версия — файл, а не константа

`tools/VERSION` содержит одну строку semver. Причины: файл виден в diff (смена версии заметна в ревью), не требует импорта и работает для скриптов, которые запускаются как `python3 tools/x.py` из любого места. Модуль `tools/coremeta.py` даёт `version()`, `version_or_error()` и `stamp()` для заголовков артефактов.

Альтернатива «версия в `pyproject.toml`» отклонена: проект не пакет, устанавливать его не нужно, а лишний файл сборки создаёт ложное впечатление установки.

### Где видна версия

- `tools/validate.py` печатает `ядро <версия>` первой строкой — так человек видит, чем проверяли данные.
- `tools/build.py` пишет `<!-- ядро: <версия> -->` в заголовок каждого сгенерированного md и в `data/dist/*.geojson` (`"core_version": "<версия>"` в properties коллекции). Это делает связь «артефакт ↔ инструмент» проверяемой, а не декларативной.
- `build.py --check` сравнивает версию в артефакте с текущей: артефакт, собранный другой версией, — расхождение. Так смена ядра заставляет пересобрать выход.

### Защита правила — по индексу git, без сервера

`tools/guard_core.py --staged` читает `git diff --cached --name-only --diff-filter=ACMR`:

- есть файлы ядра (`tools/*.py`, `tools/*.html`, `tools/release_core.py`) и нет изменения `tools/VERSION` → отказ с подсказкой команды;
- изменение только `tools/VERSION`/`tools/CHANGELOG.md` → релизный коммит, пропуск;
- изменения только в данных/документации/спеках → пропуск.

Отдельный режим `--merge-base <ветка>`: сравнивает `master...HEAD` и говорит, была ли смена версии в ветке — для проверки перед слиянием. Hook ставится в `.git/hooks/pre-commit` скриптом `tools/install_hooks.sh` (в репозиторий попадает только установщик, сами хуки — нет).

Почему хук, а не CI: репозиторий живёт на двух хостингах (GitHub и GitVerse), CI на обоих настраивать ради одного правила дорого, а коммиты делает в основном агент на этой машине. Хук срабатывает до создания коммита — то есть до того, как правило нарушено; CI сработал бы после пуша.

### Релизная процедура

`tools/release_core.py --bump patch|minor|major`:

1. читает `tools/VERSION`, поднимает нужную часть, обнуляя младшие;
2. дописывает в `tools/CHANGELOG.md` запись `## <версия> — <дата>` с заготовкой перечня;
3. печатает последовательность: заполнить запись → `git add tools/VERSION tools/CHANGELOG.md` → `git commit` → `git checkout master` → `git merge --no-ff <ветка>` → `python3 tools/build.py`.

Скрипт не делает коммит сам: перечень изменений пишет человек, иначе CHANGELOG превращается в «изменения».

### Границы

| Что | Где | Куда коммитится |
|---|---|---|
| Ядро | `tools/*.py`, `tools/*.html`, `tools/install_hooks.sh` | ветка → мастер со сменой версии |
| Версия и история | `tools/VERSION`, `tools/CHANGELOG.md` | вместе со слиянием ядра |
| Контент | `data/**`, `docs/**`, `openspec/**`, `README.md` | прямо в мастер |

`tools/front-line-pixels.json` переехал в `data/calibration/` ещё раньше — данные не лежат в `tools/`, и это правило подтверждает.

### Проверки в тестах

`tests/test_dataset.py` получает класс `TestCoreVersion`: формат версии, наличие записи в CHANGELOG, поведение `guard_core` на трёх сценариях (ядро без версии, только версия, только данные) — через прямой вызов функции с подставленным списком файлов, без git.

## Риски

- **Версия в артефактах ломает `--check` при каждом релизе** — это осознанно: смена ядра обязана приводить к пересборке, иначе артефакт врёт о том, чем порождён.
- **Хук можно обойти `--no-verify`** — правило остаётся соглашением, но проверка `--merge-base` перед слиянием и `build --check` ловят обход постфактум.
- **Данные в ветке** (например, при работе над ядром понадобилось новое место) — предупреждение, а не отказ: иногда данные нужны для проверки самого ядра.

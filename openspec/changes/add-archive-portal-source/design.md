# Design

## Context

См. `proposal.md`. Текущее состояние: 8 документов, 27 событий (документ подтверждает 3), 8 источников. В Obsidian лежит выгрузка «Памяти народа»: 100 сканов на 872 МБ в `Хобби/365сд/Исходники/ЦАМО — Память народа/<передача>/<дело>/p<лист>.jpg`, машинный каталог — `data/cache/pamyat-naroda/catalogue.json` (108 карточек, у каждой: id карточки, тип, название, период, дата, дело, лист, sha256 файла, ссылка на портал).

Ограничения:

- 872 МБ файлов: проверка хешей на каждом прогоне недопустима по времени.
- Идентификатор дела портала (`208-0002511-0275`) кодирует фонд, опись и дело, но не листы.
- Типы карточек портала — своя номенклатура («Боевые приказы и распоряжения», «Карты»), не совпадающая с реестром проекта.
- Восемь документов без сканов: вносить их нельзя, иначе в данных появятся ссылки на несуществующие листы.

## Goals / Non-Goals

**Goals:**

- Внести 100 документов с проверяемыми реквизитами, ссылкой на карточку и локальным файлом.
- Идемпотентность: повторный разбор каталога ничего не дублирует.
- Видимая очередь: какие документы ещё не привязаны к событиям.

**Non-Goals:**

- Распознавание текста сканов и извлечение фактов из приказов — отдельная работа, здесь только регистрация документов.
- Автоматическая привязка документов к событиям по датам: привязка остаётся ручной и обоснованной.
- Заказ копий восьми отсутствующих дел — это внешний процесс.

## Decisions

**1. Портал — отдельный вид источника, а не `website`.** У сайта есть снимок страниц, у портала — каталог выгрузки. Смешивать нельзя: `website` требует `url` в снимке, и любой документ портала провалил бы эту проверку. Новый вид `archive-portal` несёт `portal`, `cache_path`, `fetched_at`, `query`.

**2. Идентификатор документа — от дела и листа, а не от карточки портала.** `doc-pn-208-0002511-0275-p00000003`: понятно, что это, и совпадает при повторной выгрузке. Идентификатор карточки (`map101141583`) хранится отдельным полем — он нужен для ссылки, но не для имени.

**3. Реквизиты выводятся из идентификатора дела и помечаются как выведенные.** `208-0002511-0275` → ф. 208, оп. 2511, д. 275. В примечании документа: «реквизиты выведены из пути портала». Альтернатива — оставить реквизиты пустыми с примечанием «не установлены» — отвергнута: шифр известен точно, просто не с титульного листа.

**4. Носитель — пара «карточка портала + локальный файл».** Ссылка на карточку даёт восстановимость (портал живёт), локальный файл — возможность работать офлайн и считать хеш. Проверка по умолчанию: файл существует и его размер равен записанному в каталоге. Сверка sha256 — режим `--deep`, потому что 872 МБ на каждый прогон бессмысленны.

**5. Восемь документов без сканов не вносятся.** Правило: документ без файла листа не регистрируется, а остаётся в списке `archive_order` каталога и в отчёте. Иначе появится документ, на который нельзя сослаться.

**6. Разбор каталога — инструмент, а не ручная правка.** `tools/portal_intake.py` читает `catalogue.json`, преобразует типы по реестру (`portal_types`), пишет документы в `data/documents.json`, сообщает: сколько добавлено, сколько пропущено как уже внесённые, сколько без сканов. Ручная правка 100 записей — гарантированные опечатки.

**7. Тип документа — по таблице соответствия в реестре.** «Боевые приказы и распоряжения» → `combat-order`, «Боевые донесения, оперсводки» → `operational-summary`, «Журналы боевых действий» → `combat-journal`, «Карты» → `map`, «Приказы» → `combat-order` с примечанием, «Рапорты»/«Доклады» → `other`, «Директивы» → `combat-order`, «Планы операций» → `other`, «Сведения» → `other`. Неизвестный тип портала — ошибка разбора, а не «other по умолчанию»: молчаливое сваливание в `other` скрывает пробелы реестра.

**8. Дата — период из карточки.** Портальная карточка даёт «Описывает период: 05.12.1941—06.12.1941» и «Дата документа». Берём период с точностью `range`, дату документа — в `note`. Если периода нет — дата `null`-период с точностью из одного дня документа, помеченная как выведенная.

## Risks / Trade-offs

- [872 МБ в Obsidian, а не в репозитории] → в git только каталог с хешами и путями; проверка — по наличию файла и размеру, глубокая сверка — по требованию.
- [Типы портала грубее наших] → таблица соответствия в реестре, при сомнении документ получает `other` **с примечанием**, а не молча.
- [Часть карточек — про 365 сд «упоминается на страницах»] → в `note` пишем формулировку карточки, чтобы не выдавать упоминание за документ дивизии.
- [Портал может переименовать дела] → ссылка на карточку по id устойчива к переименованию пути; путь к файлу хранится отдельно.
- [100 документов без привязки утяжелят отчёты] → очередь печатается отдельным разделом, в хронологию не подмешивается.

## Migration Plan

1. Реестр: `portal_types` (соответствие типов карточек), вид источника `archive-portal`.
2. Схемы: источник, носитель документа.
3. `tools/portal_intake.py` + проверки валидатора + отчёт в сборке + тесты.
4. Прогон разбора на реальном каталоге: 100 документов.
5. Привязка приказов и донесений 365 сд к событиям декабря 1941 — вручную, по датам и содержанию.
6. README, разбор источника, индексы.

Откат: новые документы аддитивны, события не переписываются; `git revert` прогона разбора.

## Open Questions

- Нужен ли отчёт «документы, где 365 сд только упоминается на страницах», отдельно от документов самой дивизии — решится, когда начнём привязывать.
- Хранить ли распознанный текст листов в отдельном слое (`docs/sources/pn/<deal>/<page>.md`) — возможно, но это уже другая работа.

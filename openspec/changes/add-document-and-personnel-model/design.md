# Design

## Context

См. `proposal.md` — Why. Текущее состояние: 24 события, 24 формирования, 22 места, 7 источников. Документы существуют только как текст внутри `docs/sources/` и как страницы снимка `365sd.org` (149 страниц). Реквизиты встречаются в тексте страниц: «ЦАМО РФ, ф. 3067, оп. 1, д. 6, л. 48—48 об.» (боевой приказ № 3), «Ф Р-73, оп. 2, д. 6, л. 213—215 об.» (именной список 1213 сп). Снимок сейчас хранит только текст, поэтому таблицы списков разложены по одной ячейке в строке — по колонкам их не восстановить.

Ограничения:

- Люди — это десятки записей на один список; ручной ввод без инструмента съест часы и породит опечатки.
- Автоматический разбор таблиц ошибается на слитых ячейках и «пустых» колонках, а цена ошибки — неверная судьба человека.
- Данные остаются файлами в git; проверки и сборка офлайновые.

## Goals / Non-Goals

**Goals:**

- Документ как объект с реквизитами и носителем, ссылка «событие → документы».
- Персона и запись списка как разные сущности; конфликты между списками сохраняются.
- Снимок, пригодный для разбора таблиц (HTML для страниц с таблицами).
- Полуавтоматический разбор списка: черновик + отчёт, ручное подтверждение перед записью.

**Non-Goals:**

- Автоматическое слияние персон и «угадывание» совпадений между списками.
- Загрузка сканов документов и OCR — работа с публикациями, а не с архивными образами.
- Полный разбор всех девяти списков и всех персон полков в этом change: берём два документа и один список как проверку модели.
- Модель награждений, плена, госпиталей — отдельные сущности позже.

## Decisions

**1. Три слоя и никаких сокращений: факт → документ → носитель.** Факт ссылается на источник и локатор (как раньше); документ ссылается на носитель (страница снимка или производная); событие ссылается на документы. Соблазн «просто указать url в событии» отвергнут: тогда реквизиты снова растворяются в тексте, и заказать дело по данным проекта нельзя.

**2. Реквизиты — бинарно: полные или отсутствуют.** Частичные («фонд есть, описи нет») не пропускаются: по такой заявке в архив не сходить, а в данных она выглядит как знание. Отсутствие фиксируется явным примечанием. Альтернатива — статус «частичные» с перечнем недостающего — отклонена как способ легализовать небрежность.

**3. Персона и запись списка разделены.** Персона — устойчивая личность (id, ФИО, год рождения); запись — утверждение одного списка (документ, часть, судьба, дата). Поэтому расхождение «декабрь 1941 против марта 1942» живёт как две записи, а не как спор внутри одной сущности. Это же позволяет позже связать персону с событиями `fate` (дед).

**4. Дубли персон ловятся по нормализованным ФИО + году рождения.** Нормализация: регистр, ё→е, лишние пробелы, отбрасывание инициалов вместо отчества не делается. Год рождения разделяет однофамильцев, поэтому пара «ФИО + год» — рабочий ключ. Транслитерационные и опечаточные варианты (Афонасьевич/Афанасьевич) дублем не считаются: это ручная работа.

**5. HTML для таблиц — только для страниц с таблицами.** Снимок дополняется `raw/<slug>.html` там, где есть `<table>`. Хранить HTML всех страниц дороже и бессмысленно; текст остаётся основным представлением, разметка — вспомогательным для парсера.

**6. Разбор таблиц — полуавтоматический, с обязательным подтверждением.** `tools/parse_roster.py` читает `raw/*.html`, находит таблицу, сопоставляет колонки по заголовкам, выдаёт черновик в `data/drafts/<slug>.json` и отчёт: сколько строк, сколько ячеек не распознано, какие колонки слиты. Черновик **не** попадает в `data/people.json` автоматически: перенос делает человек командой `--apply` после просмотра. Причина: в списках встречаются слитые ячейки и пустые графы, а ошибка разбора превращается в ложную судьбу.

**7. Валидатор проверяет модель, а не текст.** Новые проверки: полнота реквизитов, разрешимость носителя, ссылочная целостность событие→документ и запись→персона/документ, дубли персон, обязательность провенанса у судьбы, конфликты между записями одного человека.

**8. Сводка получает раздел «Документы».** В сгенерированной хронологии под событием печатается «тип, дата, реквизиты»; отдельный раздел перечисляет документы, у которых нет привязанных событий, — это очередь на разбор.

**9. Реестр типов расширяется, а не хардкодится.** Типы документов и формулировки судьбы живут в `data/registry.json` рядом с типами событий, чтобы добавление нового типа не требовало правки схем.

## Risks / Trade-offs

- [Парсер списков даст ложные записи] → черновик отдельно от данных, обязательный `--apply`, отчёт о нераспознанном, тест на реальной странице 1213 сп.
- [Дубли персон останутся незамеченными при разных написаниях] → нормализация ловит только очевидное; в отчёте разбора печатаются похожие ФИО для ручной проверки.
- [Реквизиты в публикации могут быть неполными или ошибочными] → реквизиты наследуют статус «черновик»; при заказе в ЦАМО сверяются с описью.
- [Рост числа файлов данных] → три новых файла вместо одного; при росте — разбиение `rosters.json` по документам.
- [HTML-файлы в снимке увеличивают репозиторий] → сохраняются только страницы с таблицами (десятки файлов, не сотни).

## Migration Plan

1. Схемы `document`, `person`, `roster`; типы документов и формулировки судьбы в реестре.
2. Снимок: сохранение `raw/<slug>.html` для страниц с таблицами; пересъёмка 365sd.org (или досъёмка разметки без повторного обхода текста).
3. `tools/parse_roster.py` + тест на странице именного списка 1213 сп.
4. Внести два документа (боевой приказ № 3; оперативная сводка штаба Калининского фронта № 61) и один список (1213 сп, 27.08.1941) с персонами и записями.
5. Привязать существующие события к документам там, где подтверждение есть.
6. Валидатор, сборка, тесты, README, индексы.

Откат: новые файлы и поля аддитивны; события без `documents` остаются валидными, откат — `git revert`.

## Open Questions

- Нужен ли документам автор/подписант (сейчас только тип и реквизиты) — решится, когда появится документ, где подпись важна для атрибуции.
- Хранить ли карты (`map`) как документы или как отдельный вид — пока идут в тип «иное».
